## 1. 传输层

| 项 | 值 |
|---|---|
| 传输方式 | 裸 TCP 长连接（无 HTTP / 无 WebSocket 握手） |
| 默认 TCP 端口 | `28765`（v2.1 起从 8765 迁移：MIUI 的 scene-daemon 长期占用 127.0.0.1:8765，通配绑定必冲突） |
| 默认 UDP 端口 | `28766`（设备发现广播） |
| 监听策略 | **两端都监听 28765，两端都能主动 connect**；见 §3 |
| JSON 帧上限 | 8 MB（`MAX_FRAME`） |
| 二进制帧上限 | 8 MB（分片实际 1 MB） |
| 字符编码 | UTF-8 |
| socket 收发缓冲 | 1 MB（两端 Session 建立/连接时设置） |

## 2. 帧格式（v2）

```
+--------------------+------------------------------+
| 4B 大端 uint32     |  N 字节 UTF-8 JSON           |
|  最高位=0 → JSON   |  （控制帧）                  |
+--------------------+------------------------------+
| 4B 大端 uint32     |  二进制载荷                  |
|  最高位=1 → 二进制 |  低 31 位 = 载荷长度         |
+--------------------+------------------------------+
```

- 二进制帧子类型（v2.2 起共三种）：

| 子类型 | 名称 | 载荷格式 | 用途 |
|---|---|---|---|
| `0x01` | 文件分片 | `[1B midLen][mid UTF-8][4B seq 大端][data...]` | 文件/文件夹传输，1MB 裸分片 |
| `0x02` | 音频帧 | `[4B seq 大端][4B ts 大端][opus...]` | 语音/视频通话的 Opus 音频 |
| `0x03` | 视频帧 | `[4B seq 大端][4B ts 大端][1B flag][N 字节 AU]` | 视频通话的 HEVC/H.264 裸流（见 §4.5） |

- `0x02`/`0x03` 的 `ts` = **发送端通话相对毫秒**（进入 TALKING 那一刻置零的单调钟；PC `CallClock`、
  安卓 `util/CallClock`），音频与视频共用同一零点。**两端各自零点**：接收端从不拿它与本端墙钟相减，
  帧龄一律走两段式（发送侧排队 + 接收侧排队）。4B 无符号 ⇒ 绝对墙钟会 49.7 天回绕，
  而单通上限 6h = 21,600,000ms，相对口径永不回绕。

- JSON 长度永远 ≤ 8MB，最高位为 0，新旧帧靠最高位区分
- v1 客户端收到二进制帧会按"非法帧长度"断链 —— **两端必须一起升级**
- **未知二进制子类型会直接 `IOException` 断链**（`readFrame` 的 else 分支）。
  因此新增子类型**必须靠 `hello` 能力位门控**：绝不对没广播 `vid=1` 的对端发 `0x03`。
- 写：`out.write(len[4])` → `out.write(body)` → `out.flush()`（每帧一次 flush）
- 读：`readInt()` 得 N → `readFully(N)`；流正常关闭时抛 `EOFException` → 返回 `null`（对端断开，非错误）

每条消息（JSON 帧）的公共字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `type` | string | 消息类型（见 §4） |
| `ts` | long | 发送端 `System.currentTimeMillis()` |
| `v` | int | 协议版本，当前 `2` |

### 2.1 传输性能设计（2026-09-13）

| 机制 | 说明 |
|---|---|
| 1MB 裸二进制分片 | 替代 v1 的 256KB base64+JSON：消除 33% base64 膨胀与 350KB 大字符串的 JSON 编解码/UTF-8 转换开销（v1 实测只能跑出无线带宽 ~35%） |
| 发送端双 4MB RAM 缓冲 | 后台线程交替读源文件：一块在发送时另一块在读盘，磁盘 IO 与网络发送重叠 |
| 接收端双 4MB RAM 缓冲 | 一块填满切另一块继续收，满块交给独立落盘线程写盘；两块都未落完才阻塞（背压） |
| 传输结束直接落盘 | file_done 时剩余不满一块的缓冲同步冲盘后再关流校验 |
| socket 缓冲 1MB | 减少系统调用次数 |

## 3. 会话建立与去重收敛

两端同时存在「监听线程」和「主动连接线程」，以覆盖两种拓扑：

- **同一 WiFi**：谁先发现对方谁主动连（也可被连）
- **手机开热点**：PC 连不上手机时，手机连 PC 的 `192.168.x.1` 网关地址

握手流程：

```
A                                     B
|---- TCP connect ----------------->|
|---- hello{id,name,model,ver} ---->|
|<--- hello{id,name,model,ver} -----|
|   （双方收到 hello 后标记 handshaked，会话生效）
```

**重复会话去重规则**（两端独立计算、结论必然一致，不会各留一条连接）：

```
preferOutgoing = (myId < peerId)
```

即：设备 ID 字典序较小的一方保留自己发起的连接，较大的一方保留自己接受的连接；被淘汰的那条直接 `close()`。这样即使 A、B 同时互连（产生 2 条 TCP），最终也会收敛为 1 条。

**多客户端冲突仲裁**（2026-09-12 起，两端对称）：同一时间每端只支持**一个对端**。当已有健康会话时，其他设备的新握手**不再挤掉现有会话**（旧逻辑下 ≥3 个客户端同时启动会互相挤掉→被挤端重连→再挤→反复连接死循环），而是：

1. 占用方回一帧 `busy{holder}` 后关闭新连接；
2. 请求方收到 `busy` 后把该 IP 加入**退避队列**（15s 内不打扰该 IP），期间转而尝试其他空闲候选；
3. 退避到期自动重试——占用的会话结束后，队列里的下一个自然连上。
4. 同设备双连接仍按上面的 `preferOutgoing` 规则去重（不受影响）。

## 4. 消息类型

### 4.1 链路控制

| type | 字段 | 方向 | 说明 |
|---|---|---|---|
| `hello` | `id,name,model,ver,vid,cam,vcodec,hs,hd,dl,dm` | 双向 | 握手，收到即视为会话建立。尾部均为能力协商字段（§4.5.1 / §4.6 / §4.7 / §4.8 / §4.9），老端忽略未识别的字段 |
| `ping` | — | 双向 | 保活，每 **15s** 一次 |
| `pong` | — | 双向 | ping 应答 |
| `busy` | `holder` | 双向 | （仅旧版本发送）拒绝连接：本机只服务一个对端。新版本收到只提示、不退避、不重试 |
| `ack` | `mid,ok` | 双向 | 对 `text` 的确认 |

**保活与判死**：双方各每 **15s** 发一次 ping，收到任何帧（含 pong）即视为对端存活。若发出 ping 后 **35s** 内未收到任何帧（连续两轮 ping 无 pong）→ 判定断链，关闭**这一条**会话（其他设备的会话不受影响）。注意判死依据是**收包**而非发包——自身 ping 只被内核 ACK，不能作为对端存活证据。断开后**不自动重连**——用户在设备列表点一下该设备才重连。

**写失败即判死**：任何一次发送抛异常，立即 `close()` 该会话——同样是只动这一条，不影响其他会话。

### 4.2 文本与剪贴板

| type | 字段 | 方向 | 说明 |
|---|---|---|---|
| `text` | `mid,text` | 双向 | 主动发送的文本 |
| `clip` | `mid,text,sha1` | 双向 | 剪贴板正文（直接推送）。**2026-09-15 起为 PC→手机的主通道**：PC 侧复制后直接推正文，手机纯被动接收 |
| `clip_notify` | `len,sha1,preview` | PC→手机 | **v2.1 起已废弃**（新 PC 不再发送）。旧语义：仅通知不带正文、手机回 `clip_pull` 取正文；新手机收到只记日志不回拉 |
| `clip_pull` | — | 双向 | 请求对端剪贴板缓冲内容，对端回 `clip_state`。**2026-09-15 起手机端不再主动发起**（读取只由焦点切换触发）；仅保留应答兼容（手机收到 `clip_pull` 仍回 `clip_state`，有焦点时回正文、无焦点回空） |
| `clip_state` | `text,sha1` | 双向 | 对 `clip_pull` 的应答，携带本端剪贴板缓冲内容；`text` 为空表示本端当前读不到剪贴板 |

### 4.3 文件与文件夹

| type | 字段 | 方向 | 说明 |
|---|---|---|---|
| `dir_meta` | `mid,name,fileCount,totalSize,dirs[,list,skipped]` | 双向 | **文件夹传输开始**：声明目录名/成员数/总字节。接收端挑定不重名的落盘目录并建一个目录气泡，成员文件不再单独出气泡。`dirs` = 空子目录相对路径（PC 端据此重建）；`list` = 成员相对路径清单（v2.6，用于缺失核对）；`skipped` = 被跳过的分支数（v2.6，>0 时对端明示） |
| `dir_end` | `mid,sent,last` | 双向 | **文件夹收尾**（v2.6）：本轮成员发完（无论成败）。`last=1` = 本端不再补发，接收端无论缺不缺都定稿 |
| `dir_missing` | `mid,items[]` | 双向 | **文件夹核对回执**（v2.6）：接收端发。`items` 空 = 确认收齐；非空 = 这些成员没到，请补发 |
| `file_meta` | `mid,name,size,mime,sha256,offset,relPath,dirId` | 双向 | 文件开始。`offset>0` = 续传（从该字节继续）；`relPath` = 目录内相对路径（文件夹成员）；`dirId` = 所属 `dir_meta` 的 mid |
| `file_chunk` | `mid,seq,data` | — | **v1 遗留，v2 已移除**。分片改走二进制帧（§2） |
| `file_done` | `mid,sha256` | 双向 | 发送完成，携带**整文件** sha256（含续传前缀）供接收端校验 |
| `file_query` | `mid,name,size` | 双向 | **断点续传询问**：发送端开传前问对端有没有半成品 |
| `file_resume` | `mid,ok,offset,sha256` | 双向 | 续传应答：`ok=true` 时 `offset` 为对端已有字节数（对齐分片边界；等于文件大小表示已收完只差确认）。`sha256` 预留（当前两端都发空串，整文件完整性由 file_done 校验兜底） |
| `file_cancel` | `mid` | 双向 | 发送方取消；`mid` 为 `dir_meta` 的 mid 时取消**整个文件夹** |
| `file_verify` | `mid,md5` | 双向 | **续传完成核对**：触发过续传（offset>0）的普通单文件，接收端把落盘文件的 MD5 回发给发送端；发送端与源文件 MD5 比对（端到端完整性二次确认）。异步发送、不占任何同步路径；旧版本对端忽略未知帧即可 |

**分片**：1 MB（`CHUNK_SIZE`）裸二进制帧，`seq` 从 `offset/CHUNK_SIZE` 起连续递增，接收端严格按 seq 顺序追加，乱序丢弃。

**断点续传流程**：

```
发送端                                接收端
|---- file_query{mid,name,size} ---->|
|   （查活动通道 → 半成品注册表）     |
|<--- file_resume{ok,offset} -------|   ok=false → 从头传
|---- file_meta{...,offset} ------->|   接收端以追加模式打开半成品
|---- chunk(seq=offset/CHUNK..) --->|   双 4MB 缓冲交替，满块异步落盘
|---- file_done{sha256} ----------->|   尾块直接落盘，整文件 sha256 校验
（offset>0 时）
|<--- file_verify{mid,md5} ---------|   接收端后台算落盘文件 MD5 回发（异步）
|    发送端后台算源文件 MD5 比对；120s 超时只记日志跳过，不改传输状态
```

- 发送端读源文件 `[0, offset)` 只为计算整文件 sha256 的前缀段（不发送），读失败改从头传
- 接收端半成品注册表持久化（PC `pc/partials.json` / Android `filesDir/partials.json`），每次落盘刷新；file_done 校验通过或 file_cancel 时清除
- 校验失败且来自续传 → 删除半成品，下次自动从头传
- **待发队列先入后删（防强杀，2026-09-13）**：普通单文件/文件夹**开传前**就写入持久化待发队列，发送成功才移除 —— 任何时刻被强杀（含传输中途），重启后握手自动补发、同 mid 命中半成品无缝续传。补发与在途传输用 inFlight 集合去重；MD5 不一致时发送端气泡标 FAILED
- 已知边界：文件夹的 dirSendState 是内存态，发送端重启后已完整送达的成员会整文件重传一遍（对端产生重复副本，不影响正确性）

**文件夹传输**：接收端把成员落到 `<接收目录>/<文件夹名>/<relPath>`（PC 建真实目录，Android 走 MediaStore `RELATIVE_PATH` 子目录），文件夹名重名自动加 ` (1)` 序号；目录气泡按已收字节聚合进度，成员全部完成后标完成。取消整目录时删除已收成员/半成品并两端同步移除气泡。

**成品目录保留**（v2.6）：接收端收尾后**不从 `dirMap` 删除**目录记录，同一 `mid` 重发（断链后从待发队列补发整目录）时**就地复用原目录** —— 否则会另建「文件夹 (1)」，用户看到的正是「原文件夹里少了文件」。成品记录限量回收（`MAX_KEEP_DIRS = 32`，按收尾时间淘汰最旧）。

发送顺序严格为 `dir_meta → (file_meta → chunks → file_done)×N → dir_end`（成员逐个串行，`dir_end` 仅对 `dl=1` 的对端发送）。

**成员失败的两类处理**（v2.6）：
- **本地源不可读**（文件被删 / 无权限 / SAF 授权失效）：**只跳过该成员并继续发其余成员**，最后统一汇报。老逻辑「一个坏文件 ⇒ 整目录停摆」会让后面所有成员一个都发不出去。本地错误**不关闭连接**（链路本身是好的），也不进待发队列（重试同样失败），并给对端发一帧 `file_cancel` 清掉已建好的半成品。
- **网络异常**：整目录中止、进待发队列，重连后凭半成品续传重来。

**扫描端不得静默丢弃**（v2.6）：枚举目录树时，**读不到**（query 抛异常 / 游标为 null / 条目字段缺失）与**真的是空的**必须区分开 —— 前者计入 `skipped` 并在 `dir_meta` 里带给对端，后者才写进 `dirs`。老逻辑把「枚举失败」当成「空目录」，对端照重建出一个空文件夹，用户看到「文件夹在、里面的文件不见了」。同理，一个文件都没扫到却又有读失败时，**直接中止发送并提示**，而不是发一个 `fileCount=0` 的「成功」。

接收端拼装完成后校验整文件 sha256，一致则落盘并回 `ack{mid, ok=true}`，不一致则标记 `FAILED`（续传场景还会删半成品）。

**取消语义**（`file_cancel`，2026-09-13 起）：发送方在气泡上点「取消」后
① 立即中断本端分片发送循环（`file_chunk` 不再继续）；
② 发一帧 `file_cancel{mid}`；
③ 本端把该条消息从聊天界面移除、从 `pending` 队列移除、从 `history` 删除。
接收端收到 `file_cancel` 后：若正在接收则关闭输出流、**删除半成品文件**、从 `rxMap` 移除；
无论是否还在接收，都把该 `mid` 的气泡移除并删除本地历史记录 —— 即**双方同步取消、两端都不显示**。
`file_cancel` 对未知 `mid` 是幂等的（只做删除展示/历史，不报错）。

### 4.5 语音 / 视频通话

#### 4.5.1 能力协商（`hello` 扩展字段）

| 字段 | 类型 | 说明 |
|---|---|---|
| `vid` | 0/1 | 本端**可接收**视频。**对端没有这个字段（老版本）时一律视为 0** |
| `cam` | 0/1 | 本端**有摄像头、可发送**视频。PC 端恒为 0（只收不发） |
| `vcodec` | string[] | 本端**可解码**的编码列表，如 `["hevc","h264"]` |

> **这是新增二进制子类型的唯一安全闸门。** `readFrame` 遇到未知子类型会直接
> `IOException` 断链，所以 **只有对端 `vid=1` 时才允许发 `0x03` 视频帧**。
> 老版本对端不认识这些字段 → 天然忽略 → 永不断链，向后兼容成立。

#### 4.5.2 控制帧

| type | 字段 | 方向 | 说明 |
|---|---|---|---|
| `call_invite` | `name,ip,vid,lv` | 呼出→被叫 | 呼叫请求。`vid=1` 为视频呼叫；`lv` 为呼叫方本次选的档位上限（0/1/2/3，见 §4.5.4） |
| `call_accept` | `vid,lv` | 被叫→呼出 | 接听。`vid` 两端取与；`lv` 两端取 min |
| `call_reject` | — | 被叫→呼出 | 拒接 |
| `call_busy` | — | 被叫→呼出 | 忙线（已有通话），静默拒绝 |
| `call_end` | `reason` | 双向 | 挂断。`reason` 可为 `record_fail`（对方无法访问麦克风）/`timeout`（6h 上限） |
| `call_cancel` | — | 呼出→被叫 | 接听前主动取消 |
| `video_cfg` | `codec,w,h,fps,br,rot,cam` | 发送→接收 | 编码参数（变更时重发 + **发送端每 1s 心跳重发**，2026-09-22 加，保证接收端 rot/cam 最终一致；值没变时接收端无动作）。`br` 单位 **kbps**；`rot` 为画面需旋转角度（**2026-09-22 二期起语义变更**：Android 发送端 GL 已把数据转正，`rot` = 在正立数据之上还需顺时针补的角，**新版恒发 0**；老版本语义为「逆时针转多少度才正」）；`cam` = **本端摄像头朝向**（1 前置 / 0 或**缺省**后置，2026-09-19 加） |
| `video_fb` | `fps,drop,lat,dropping,kbps` | 接收→发送 | 接收侧健康反馈，每 2s 一次。`drop` 丢帧百分比、`lat` 排队延迟 ms（**真实值**，不再用 -1 当丢帧哨兵）、`dropping` 接收端此刻是否正处于**丢帧期**（布尔，与 `lat` 分开的独立标志；**老对端不带此键 = false**）、`kbps` 实际接收码率 |
| `video_req` | `on` | 接收→发送 | 请求对端临时停/开视频（如接收端切后台） |

状态机两端同构（`IDLE/OUTGOING/INCOMING/TALKING`），**全局单通话**：
新呼出在忙时直接拒绝；新呼入忙时回 `call_busy`。6 小时强制挂断 + 60s 振铃超时。

#### 4.5.3 视频二进制帧（`BIN_VIDEO = 0x03`）

```
+--------+----------+-----------+---------+-------------------+
| 1B sub | 4B seq   | 4B ts(ms) | 1B flag | N 字节载荷        |
|  =0x03 |  大端    |   大端    |         | HEVC/H264 Annex-B |
+--------+----------+-----------+---------+-------------------+
长度字段 = 0x80000000 | (1 + 4 + 4 + 1 + N)
```

- **一个包 = 恰好一个访问单元（AU）**。所以接收侧**不需要**扫 `00 00 01` 起始码，
  直接把载荷喂给解码器即可（PC 端即 `ffmpeg -f hevc -i pipe:0`）。
- `ts` = **发送端**通话开始以来的毫秒（`CallClock`，与同一通话的音频帧同零点，单调），用于 A/V 时间轴对齐。
- `flag` 位定义：

| bit | 名称 | 含义 |
|---|---|---|
| 0 | `VIDEO_FLAG_KEYFRAME` | 该帧为 IDR（接收端用于丢帧后对齐） |
| 1 | `VIDEO_FLAG_CONFIG` | 载荷是参数集（VPS/SPS/PPS），收到即（重）配置解码器 |
| 2-7 | 保留 | 必须为 0 |

- 单帧**硬上限 128 KB**（与音频/文件分片共用 `writeLock`，必须限长避免一次写锁长时间独占）。
  ⚠ L3（5M）的 IDR 约 250KB ⇒ 带内档会更常整帧丢关键帧（计入 `videoDroppedByGate`，并由
  `onLocalDrop()` 自动降回 L2）；UDP / 媒体 TCP 档走 1188B 切片重组，不受此闸门限制。
- **不做应用层重传**：媒体走 TCP，重传由协议栈完成且无重复；应用层"立即重发"只会
  发重复帧、并在拥塞时把字节数翻倍。改用**发送截止期**——单帧写入耗时超 100ms 记 drop
  并纳入降档判据（`video_fb`）。

#### 4.5.4 档位与音频

| 档 | 分辨率 | 帧率 | 视频码率 | 音频 Opus | 说明 |
|---|---|---|---|---|---|
| L0 | 640×480 | 30 | 500 kbps | 32 kbps | 下限（「流畅 480P」）。⚠ 2026-09-16 起从 854×480 改 VGA：854×480 **不是标准相机流尺寸**（a12/a16 的 StreamConfigurationMap 都没有）且非 16 对齐常被硬编拒 → 480P 档黑屏 |
| L1 | 1280×720 | 30 | 1500 kbps | 64 kbps | 「标清 720P」 |
| L2 | 1920×1080 | 30 | 2000 kbps | 64 kbps | **起始档基准**（「高清 1080P」，选档框标「（推荐）」） |
| L3 | 1920×1080 | 30 | 5000 kbps | 64 kbps | 「超清 1080P」（2026-10-03 加）：分辨率与 L2 相同，升降这一档只动码率 |

- **用户选的档 = 本次通话的上限**：自动升降档都不越过它；即便选了 L3，**起始**仍最高从
  L2（2M）出帧，网络持续健康才由状态机升到 L3。

- GOP = 1s（30 帧）；码率模式 **CBR**；`KEY_LOW_LATENCY=1`（API 30+）。
- **档位 = 真分辨率切换**（2026-09-15 起，原「一期固定 720p 只切码率」已作废）：
  升降档逐级进行（超清 ↔ 高清 ↔ 标清 ↔ 流畅）。只变码率时走 `setParameters()`（零中断）；
  分辨率变化时重建编码器 + `capture.updateTargets()`（画面中断约 200–400ms），
  并重发 `video_cfg` —— 接收端按 `w/h` 变化重建解码器，收到的是**新一套参数集**。
  ⚠ L3 ↔ L2 分辨率一致 ⇒ 这一级永远是「只变码率」，不重建编码器也不重发尺寸。
- `lv` 越界一律收敛到最近档（`of(idx)` 不抛异常，索引来自对端 JSON）。
  老版本只认 0/1/2：收到 `lv=3` 会夹到它表里的最高档（= 高清 2M），不会崩、不会黑屏。
- PC 端没有档位表，`lv` 由 `video_cfg.br` 反推（阈值 = 本表码率原值 500/1500/2000/5000kbps），
  改本表码率必须同步改 `CallManager.onVideoCfg` 的那串阈值。
- **音频帧长随通话类型变**：语音通话 **200 ms**（=10×20ms Opus 子帧）；
  **进入视频通话后两端切 40 ms**（=2×20ms 子帧），用于压缩唇音同步偏差。
  子帧仍为「2B 长度前缀 + Opus 数据」，seq/ts 语义与严格按序播放逻辑均不变。
  该常量是**收发两端硬对称**的，但视频通话只可能发生在双方都是新版本时，
  因此不存在跨版本兼容问题。
- **视频通话**：音频码率随档位联动（`OpusEncoder.setBitrate`），**对解码端完全透明**，
  切换不重建解码器。
- **纯语音通话**：起步 **64 kbps**，Android 端由 `VoiceBitrateController` 自适应
  降到 **32 kbps**（判据 = 发送阻塞 2s 均值 >120ms / 播放队列积压 ≥2 帧 / 缺帧率 >15%，
  拥塞连续 2 次采样降档；健康窗口 15s 且间隔满足才升回）。PC 端暂不变（恒 64k）——
  码率对解码端透明，两端**不需要**同步该策略。

#### 4.5.5 `rot` 的方向语义（易错点，2026-09-15 三次修订）

`rot` = 接收端把画面旋转多少度才是正的（0/90/180/270）。发送端算法：

```
base = SENSOR_ORIENTATION(后摄 -display / 前摄 +display)
rot  = (base + trim) % 360          // trim = 用户手工纠偏，默认 0
```

**⚠ 方向基准以 PC 端为准**（2026-09-15 实测：PC 用 `Graphics2D.rotate(rot)` 显示正常，
而 Java2D 正角是**逆时针**）→ 因此 `rot` 的实际语义是「**逆时针**转多少度才正」，
不是文档早期写的「顺时针」。Android 端 `Matrix.postRotate` 正角是**顺时针**，与 PC 相反，
所以 Android 渲染侧必须**取负号**（`rot → -rot`）才能和 PC 对齐。

三条硬约束：

1. **`display.rotation` 必须是真实值**。Android 侧本类是**应用上下文**，
   `Context.getDisplay()` 在 API 30+ 恒抛 `UnsupportedOperationException` → 回落 0 →
   等于**永远按竖持判定**，横持时对端画面恒定歪 90°。必须用
   `DisplayManager.getDisplay(DEFAULT_DISPLAY).rotation`。
2. **握姿变化要重发 `video_cfg`**。2026-09-22 二期起发送端 **GL 转正**（`GlRotatePipe`，
   相机帧先旋转再喂编码器，微信同款）——采集角随握姿变化时 GL 同步改角度，数据保持正立，
   `rot` 恒发 0；接收端只更新 `rot`（**不重建解码器**）。
3. **本地预览与远端不再共用同一套补偿**（二期起分家）：远端主画面 = GL 转正后零旋转；
   本地小窗仍吃原始缓冲，沿用 `-rotationDegrees() + 90`（前置 +180、水平镜像）。
4. **Android 本地预览渲染取负号**（2026-09-15 定调，现仅预览路径使用）：`rot * ROT_SIGN`。
   二期起远端主画面默认角 = `remoteRotation`（新版恒 0），不再过这个符号。
   之前「+90 / -90 / +180」公共补偿/按朝向补角全部废弃。
5. **`cam` 现在只做朝向通知与槽位记忆**（前置/后置手调槽仍保留）：二期数据已转正，
   接收端不再按朝向改默认角；PC 端 2026-09-22 起 `cfgRot = rot`（去掉前置 +180）。
   - 发送端**切摄像头时必须重发 `video_cfg`**（`cam` 更新），否则接收端朝向信息滞后。
     分辨率/码率没变 → 接收端**不重建解码器**。
   - **兼容**：`cam` 是 JSON 新增键，老对端按缺省 0（后置）处理 → 行为与改造前完全一致，
     不需要 hello 能力位门控（也不引入新的二进制子类型）。

**另（2026-09-19）**：Android 端「本地小窗」的手调旋转角按**本机**前后摄分两套
（`Prefs.rotLocalOf(key, front)`，存储键 `组键|f` / `组键|b`），老数据（裸组键）只提升为
**后置**那套。

**另（2026-09-15）**：应用 `MainActivity` 已锁 `screenOrientation="portrait"`（强制竖屏），
`display.rotation` 恒为 ROTATION_0，`rotationDegrees()` 对后置恒 = SENSOR_ORIENTATION（稳定值），
不再随握姿跳变。

### 4.6 历史同步（hsync，v2.3）

**目的**：连接建立后，双方聊天窗口内容自动对齐 —— 无论消息是「发了没送到」还是
「一端清空/重装丢了」，下次连上自动补齐；重放/重发也不会产生重复气泡。

**唯一判据 = 统一消息 id（mid）**：两端 `newMid()` 同构，均为 `UUID` 去横线的
32 位十六进制全局唯一串（2026-09-16 定版；旧 12 位 mid 仍在旧历史里，字符串比较天然兼容）。
接收查重（`Store.hasMid`）、待发队列、历史合并（loadHistory 后行胜出）、hsync 补齐共用同一判据。

**能力位**：`hello` 增加 `hs: 1`。只在**双方** hs=1 时启用；老端不认识这些帧，
走 default 只记日志，天然兼容。

流程（两端对称，各自独立执行一遍）：

```
A                                        B
|---- hello{..., hs:1} ----------------->|
|<--- hello{..., hs:1} ------------------|
|---- hsync_mids{mids:[…]} ------------->|   A 持有的该对端 mid 清单（最近 300 条 TEXT/FILE）
|<--- hsync_mids{mids:[…]} --------------|   B 同样报一遍
|    （各自算差集：对方的清单 − 自己的历史）
|<--- hsync_pull{mids:[缺失…]} ----------|   A 请求 B 补齐（单次 ≤200 条，超出等下次连接）
|---- hsync_pull{mids:[缺失…]} --------->|   B 同样请求 A
|    （持有方按 mid 回查自己的历史）
|<=== 文本: hsync_msg{items:[…]} ========|   dir 为**对端视角**（本端 SELF ↔ 对端 PEER 互换）
|<=== 图片: file_meta/chunks/file_done ==|   沿用现有文件管线按**原 mid** 重发（≤64MB）
|    （接收端按 mid 查重：已有的丢弃，缺的落库 + 气泡，按 ts 重排）
```

规则与边界：

- `hsync_msg.items[]` 成员字段：`mid, dir(对端视角), kind("TEXT"), text, ts`。
- **参与对账/补齐的消息只有「文本 + 图片」**（v2.4 收窄，按文件名扩展名判定：
  jpg/jpeg/png/gif/webp/bmp/heic/heif/avif）。非图片文件与文件夹**绝不**跨端补齐 ——
  未完成的传输由待发队列 + 断点续传兜底（与消息状态无关），已完成的文件记录不参与任何同步。
- 图片补齐**复用普通文件发送管线**（断点续传 / sha256 校验 / 待发兜底全继承），
  接收端凭 file_meta 里的原 mid 生成气泡。注意：图片补齐的气泡方向恒为「从对端收到」，
  若缺的那条原本是接收端自己发出的（如对端清空记录后找回），方向显示会与历史不同 —— 内容优先。
- 源文件已不可读的历史条目跳过不补（不进发送管线，避免误判会话死亡）。
- CLIP 与文件夹气泡不参与 hsync。
- 会话建立时序上 hsync 在 flushPending（待发补发）之后执行；两者都以 mid 查重兜底，不会重复。

### 4.7 消息删除同步（v2.4）

**目的**：删除一条文本/图片时，让在线对端同步移除，而不是被 hsync 又补回来。

**能力位**：`hello` 增加 `hd: 1`。只在**双方** hd=1 时发送 `msg_del`；老端不认识该帧，
走 default 只记日志，天然兼容（它们也不会发，删除退化为「只删本机」）。

| type | 字段 | 方向 | 说明 |
|---|---|---|---|
| `msg_del` | `mids[]` | 双向 | 通知对端「这些消息已在本机删除」。只对**文本/图片**发；文件与文件夹的删除不发此帧 |

语义（两端对称）：

- **双方在线时删除**：删除方本地清理（气泡 + 历史 + 待发）后发 `msg_del{mids}`，
  对端收到后同样清理三处 —— 双方同时消失。下次连接双方 mids 清单里都没有它，不会被 hsync 复活。
- **对端离线时删除**：发不出帧，只有本机删了。下次连接对端的 hsync_mids 仍含该 mid
  → 差集补齐 → **这条文本/图片会自动同步回来**（对端历史里还在；图片走原 mid 文件管线，
  源文件已被对端删除则跳过不补）。这是预期行为，不是 bug。
- 接收端处理 `msg_del` 只清本地，**不再回传** —— 无回环；对未知 mid 幂等。
- 文件/文件夹的删除只影响本机记录，不传播、不被补回；已落盘的实际文件一律不动。

**「清空会话」必须走这条通道（2026-09-21 PC 端定调）**：清空 = 把本会话**每一条**记录的 mid
枚举出来逐条删（`ChatWindow.clearCurrentConversation` → `Link.deleteMessages`：本地一次清完，
文本/图片按 200 条分片发 `msg_del`），**不是**把历史文件整删。整删只清本机，对端清单里那几条
还在 → 它下次一连上就 hsync 补回来（用户报的「对方设备一启动就同步回来了」）。

- **发 `msg_del` 的边界**：只有「文本 + 图片」进 `mids[]`（与参与 hsync 的类型完全一致）；
  文件/文件夹/剪贴板/通话记录只删本机 —— 发过去会让对端删掉不该删的记录。
- **对端离线时**发不出帧，此时清空只清本机，文本/图片下次连接仍会被补回（本节的既有语义）。
  UI 必须在确认框与结果提示里**如实说明**（在线 = 「会一起清掉」；离线 = 「只清了本机」），
  不能假装清干净。
- 批量清空时**一帧可带多条 mid**（`mids[]` 是数组，PC 按 200 条分片、Android 同
  `Link.MSG_DEL_CHUNK = 200`），不必一条一帧。

> ✅ **两端已对齐（2026-09-21）**：PC 端 `ChatWindow.clearCurrentConversation()` →
> `LinkHsync.deleteMessages()`；Android 端 `AppCore.clearHistory()` / `confirmClearHistory()`
> → `Link.deleteMessages()`（枚举 → 确认框 → 本地一次清完 + 分片发 `msg_del`）。
> 两端都不再整删历史文件，`Store.clearHistory(...)` / `Store.clearConversation` 已无 UI 调用点。

### 4.8 文件夹完整性校验（v2.6，仅双方 `dl=1` 时启用）

**要解决的问题（2026-09-16）**：老流程里发送端只要把 `file_done` 写进 socket 就当成功，
**完全不等接收端确认**；接收端建文件失败 / 落盘失败 / 校验失败时只在本地记一行日志，
发送端照样报「文件夹发送完成」。结果就是用户报的「**传文件夹会漏掉部分文件**」，
且两端都不知道少了哪些。

**能力位**：`hello` 增加 `dl: 1`。只在**双方** dl=1 时发送 `dir_meta.list` / `dir_end` /
`dir_missing`；老端不认识这些字段与帧（JSON 控制帧的未知 type 只记日志、**不断链**）。

```
发送端                                        接收端
|-- dir_meta{mid,name,fileCount,totalSize,list,skipped} -->|  建目录气泡 + 记住成员清单
|-- file_meta → chunk… → file_done  （×N 个成员，逐个串行）-->|  每收一个：成功进 got / 失败进 bad
|-- dir_end{mid,sent,last=0} -------------------------->|  本轮发完 → 用 list 求差集
|<------------- dir_missing{mid,items=[缺失项]} ---------|  非空 = 请补发这些
|-- file_meta → … → file_done （只发缺失项）------------>|
|-- dir_end{mid,sent,last=1} -------------------------->|  最后一轮 → 接收端无条件定稿
|<------------- dir_missing{mid,items} ----------------|  最终回执（空 = 收齐）
```

- 接收端以 `list` 与**实收清单**（`got` + `bad`）求差集：`bad`（落盘/校验失败）也算「到过」，
  但仍会回给发送端补发一次。
- 缺失项补发最多 **2 轮**（`DIR_RESEND_ROUNDS`），之后 `last=1` 定稿：
  接收端把气泡标 `FAILED` 并把缺失文件名（前 20 个）写进日志；发送端同样标 `FAILED` 并列出。
- `list` 过大（超过 2 MB 文本量）时**不带清单**，退化为「按数量核对」：接收端只比对
  `doneFiles` 与 `fileCount`，缺件时回不了具体文件名，日志里明确说明「无法精确定位」。
- 发送端等回执有超时兜底（有清单 60s / 无清单 5s）：超时按「已发送」定稿，不阻塞线程。
- **兼容**：对端 `dl=0`（老端）时发送端完全走老路径（不发 `dir_end`、不带 `list`），
  接收端仍保留 `doneFiles >= fileCount` 的兜底收尾 —— 新老混搭可用。

### 4.9 数据流量使用确认（v2.7，仅双方 `dm=1` 时启用）

**要解决的问题（2026-09-17）**：用户不希望「在不知情的情况下为一次传文件/通话花掉蜂窝流量」。
旧实现只有「同对端本次运行内提醒一次」的记忆逻辑，太弱；用户明确要求**每次使用都提醒一次、
双向都要提醒**，并且拒绝时要让**对端如实知道是被拒了**（而不是默默失败或静默无响应）。

**判据是「两端各自的网络环境」**，不是对端 IP 网段 —— 老实现用「对端 IP 不在局域网段」来猜，
在「手机热点 / 跨网段局域网」下会误判。新实现由**每端自己**回答「我在运营商数据网络上吗」。

**能力位**：`hello` 增加 `dm: 1`。只在**双方** dm=1 时才走 `data_ask` / `data_ans`；
对端是老端（`dm=0`）时回落到改造前的口径（对端 IP 非局域网段 → 只提醒本机）。

```
发起端                                        对端
|-- data_ask{mid,kind,name,size} ---------------------->|
|                       对端不在数据网络 → 立即自动同意 |
|<------------- data_ans{mid,ok} -----------------------|  在数据网络 → 先问它自己的用户，再回 ok
   ok=1 → 真正开始（file_meta / call_invite…）
   ok=0 → 如实提示「对方拒绝了使用数据流量接受X」
```

**帧字段**：

| type | 字段 | 方向 | 说明 |
|---|---|---|---|
| `data_ask` | `mid,kind,name,size` | 发起方→对端 | 征求「本次操作是否可以用数据流量」。`kind` ∈ `file`/`voice`/`video`；`name`/`size` 仅文件用（确认框里带上文件名/大小） |
| `data_ans` | `mid,ok` | 对端→发起方 | `ok=1` 同意、`ok=0` 拒绝。`mid` 与 `data_ask` 同一个（同时也是本次传输的 mid，便于对账） |

**两端行为约定**：

- **每次使用都提醒一次，不记忆**：`data_ask` 是**每次操作一个新 mid**，不缓存「这个对端同意过」。
- **双向提醒**：本机在数据网络 → 本机也提醒本机用户（发起方向）；对端在数据网络 → 由 `data_ask`
  让对端提醒它的用户（接收方向）。所以「接听语音/视频/文件」同样会被提醒到。
- **对端不在数据网络时零打扰**：立即回 `ok=1`，发起方不弹任何框。
- **拒绝时接收端什么都不记录**：接收端拒绝 → 只回 `data_ans{ok:0}`，**不生成气泡、不写历史**
  （避免留下一条「自己没收成却存在于聊天里」的幽灵记录）；由发起方那边如实提示。
- **文件被拒 → 消息留在聊天里**：发送方该条消息置 `DENIED`，气泡末尾显示**红色感叹号（矢量绘制，
  等价于一张 SVG）**，点一下重试。重试会**完整重走一遍** `data_ask`（本机提醒 + 对端确认）：
  再次被拒 → 保持 `DENIED`（表现与第一次完全一致）；同意 → 先**把这条消息移到时间线最末**
  （`onMessageMoved` 事件驱动界面摘下重挂并刷新时间），再从 `PENDING → SENDING` 开传。
- **通话也以消息记录**：通话结束时本机记一条 `kind=CALL` 的消息，文本形如
  「语音通话 00:12」；未接通则记「语音通话 对方拒绝了使用数据流量」/「…未发起（未同意使用数据流量）」。
  **只记本机，不参与 hsync**（协议零字段、不跨端同步）。
- **其余情况与 WiFi 完全一致**：一旦同意，不做任何限速/限功能处理。
- **超时一律按「未同意」处理**：`data_ans` 等待上限 90s（Android 端 `DATA_ANS_WAIT_MS`），
  超时或发送失败都不偷偷花流量。
- **线程红线**：发起方等待 `data_ans` 是**阻塞**的（本机弹框也要等用户点），因此
  `ensureDataConsent` **绝不能在主线程 / 网络读线程 / `io{}`（pp-send 单线程）里调用**，
  调用点一律用专用线程；`data_ans` 必须直接投进等待信箱，**不能过 `ui{}`** 或任何可能被拖延的队列。
- **PC 端恒在局域网**：PC 本机从不弹框，只会发 `data_ask` 去问对端（PC 无视频采集能力，
  因此 PC 只会发 `kind=voice` / `kind=file`）。
- **兼容**：对端 `dm=0` 时两端都不发 `data_ask`（老端收到未知 type 只记日志、不断链）。

## 5. UDP 设备发现

- **启动时广播一次** beacon（内容同 `hello`：`id/name/tcpPort/udpPort`），之后**纯被动接收**——没有周期广播、没有轮询
- beacon 可带 `q:1`（主动扫描询问标记）；收到带 `q` 的 beacon 后**回一次自己的 beacon**（同样以广播发出、**不带 `q`**，按来源 IP 2s 限频 → 被反复唤醒也不会刷包，且不会互相反弹）
- 收到 beacon 即把来源 IP 加入**设备列表**（去重、记 lastSeen），被动接收常驻，随时能把新上线的设备唤醒进列表
- 发现不是连接的前提，只是"设备列表自动补全"；没有发现也能靠手填 IP 连通

### 5.0 主动扫描的两条路径（2026-09-21）

启动时（Android 另有「回前台自愈」）跑一次有界扫描，窗口内**两条路径合并成一次结果**：

| 路径 | 发到哪 | 为什么还要它 |
|---|---|---|
| ① 广播询问 | 各网卡广播地址 + `255.255.255.255`（UDP 28766） | 一次发包覆盖整个广播域（老路径） |
| ② **网段扫描** | 本机地址所在 **/24** 的 `.1`~`.254`，逐地址**单播**同一个询问帧 | 广播在 AP 隔离 / 交换机 IGMP 抑制 / 大子网（如 /16）里常到不了对端；单播直接命中 |

- **只扫最后一段**：本机 `10.1.2.3` → 只扫 `10.1.2.1`~`10.1.2.254`（跳过自己；`.0` 网络号与 `.255` 广播不发）。
  子网掩码只决定广播地址，不改变这条规则 —— 掩码是 `/16` 时也只扫自己那 `/24`。
- **闸门**（不满足即跳过，并如实提示，不发包）：
  - 本机 IPv4 必须落在私网段 `10/8`、`172.16/12`、`192.168/16`；公网 / `169.254/16` / IPv6 一律不扫。
  - **Android 额外要求本机已连 WiFi / 热点 / 有线以太网**：手机走运营商数据网时自身地址常常就是 `10.x`（CGNAT），照扫会白打 254 个运营商侧地址。
- 发包节流：每 16 个地址歇 8ms；窗口过半时对**还没回应的地址**补扫一轮（首轮可能因 ARP 未收敛丢包）。
- **协议无新增字段**：网段扫描复用 `q:1` 询问帧，对端逻辑不变 ⇒ **老版本对端也能被扫到**。

### 5.1 会话模型（v2.1，2026-09-13）

- **多设备独立 TCP 长连接**：一台设备可同时与多台对端各保持一条会话，互不干扰；一条会话断开不影响其他
- **消息归属 = TCP 会话本身**（帧里没有路由字段）：A→B 的内容 C 收不到，也不会写进 C 的聊天记录；历史按**设备**分文件（PC `history/<deviceId>.jsonl`、Android `history/<deviceId>.jsonl`，见 §5.2）
- **连接只由用户点击触发**：点设备列表里的一台 = 选中它并（若未连上）连接一次，失败不自动重试；没有后台自动重连循环
- `busy` 帧仅由**旧版本对端**发出，新版本收到只提示不退避

### 5.2 设备身份与分组（v2.5，2026-09-16）

**协议无新增字段**：`id` 早在 v2 初版就存在于 `hello` 与 UDP beacon 里，这一节只是把它
的**用法**定死，两端实现对称。

**身份**

- 每端设备 id = **首次启动应用时随机生成**并落盘（Android `Prefs.deviceId` → `android-xxxxxxxx`，
  PC `Store.deviceId` → `pc-xxxxxxxx`），**卸载前不变**；没有 id 就生成一个。
- 出网时它出现在两处：TCP `hello.id`、UDP beacon `id`（两处都只写自己的）。

**绑定（连接时自动发生，无需用户操作）**

- A 连上 B 后，B 收到 A 的 `hello` → 把 `A的来源IP → A的id` 记进本机权威绑定表；
  UDP 发现路径同理（beacon 带 id）。
- 绑定表是**本机私有状态**，不在协议里交换：对端不知道也不需要知道「哪些 IP 被本机归成了一组」。

**分组**

- 同一个 id 被绑到多个 IP ⇒ 这多个 IP 是**同一台设备的多个地址**（WiFi / 热点 / USB 网卡…），
  自动成组。组键 = 对端 deviceId；**未绑定过的地址**回退用 IP 当组键（行为与 v2.4 之前一致）。
- **本端删掉一个地址（移除地址 / 删除设备）时同时解除它的绑定**：绑定表是本端对「这个地址是谁」
  的权威答案，留着不删的话，用户之后手动把同一个地址加回来会**立刻并回老那台设备的组**。
  解绑只发生在本机，对端无感知；那个地址下次广播/握手时会被重新绑定（届时可能绑到别的 id）。
- 按组键归并的东西：聊天记录文件、待发队列、消息归属判定、**备注**、**组内当前地址**、
  视频旋转角记忆。
- **同组回落**：向「某个地址」找会话时，若该地址没有健康会话，会回落到**同组键**的任意健康
  会话。这样用户把当前地址切到同设备的另一个（比如切到热点地址）后，收发与通话仍走实际可达
  的那条会话，不会因为点错地址就「设备明明在线却发不出去」。
- **并入已有设备时要迁移本端状态**：手工添加的地址、或刚建连还没握手的行，其组键原本是 IP
  自己；一旦对端自报的 id 本机**早就认识**，这个地址就并进那台设备（组键 IP → deviceId）。
  此时「旧地址组」上的**备注 / 组内当前地址 / 视频旋转角**要一并搬到目标设备（目标已有值则
  不覆盖），否则用户写过的备注会留在旧组键上取不出来。
- **并入后要重新打开这台设备的聊天界面**：组键一变，聊天记录文件、待发队列、旋转角读的都是
  另一份；不重载就会停在旧组键读出来的空列表上（看着像「记录丢了」）。
- **启动清理陈旧地址（纯本机行为，对端无感知）**：每次启动清一次 —— 只清**有 3 个以上地址**
  的设备（两条及以下整体跳过），删掉 **5 天没用过**的地址，且保底留最近使用的两条 + 当前
  使用的那条；删除同一并解除该地址的绑定。

**备注隔离（硬规则）**
- 备注是「对**对方设备 id**的备注」，**仅本机可见**：它只写在本机的持久化里，
  **绝不出现在任何出网字段**（`hello.name` / `beacon.name` / `call_invite.name` 一律用本机
  `deviceName`）。用户给对端起的备注不会泄给对方，也不会被对方的任何逻辑读走。
- 通话界面里显示的对端名字：**优先本机备注**，没有备注才回退对端自报的 `hello.name`。


## 6. 剪贴板同步语义（两端对称，防回环）

这是本协议最容易写出死循环的部分，规则如下：

**PC 侧**（2026-09-15 定版）
1. 400 ms 轮询系统剪贴板
2. 内容变化 → 存入内存缓冲（**只保留最新一条**），`sha1` 记入 `suppressSha1`
3. **直接推 `clip` 正文**给当前对话设备（旧版只发 `clip_notify` 让手机来拉，已废弃）
4. 手机 `clip_pull` 时仍回 `clip_state(text, sha1)`（兼容）
5. 由本端写回剪贴板的内容（即刚收到的手机剪贴板）不会再触发推送

**手机侧**（2026-09-15 定版：**读取只由焦点切换触发，接收纯被动**）

1. **焦点切回自身**（onResume / onWindowFocus(true)，2s 去抖 + sha1 去重）→ 读一次本机剪贴板，`sha1` 与 `lastPushedSha1` 不同 → `clip` 推送正文。不轮询、不注册变化回调、不主动拉取
2. 收到 `clip` / `clip_state` → 纯被动写入本机剪贴板（写不受前台限制，后台也能收），并把该 `sha1` 同时记入 `lastPushedSha1` 与 `lastPulledSha1`
3. 其余时刻（切后台/失焦/小窗）不读不推：离开应用不补推，内容等下次焦点切回时再同步

**剪贴板同步模式（手机端总开关，默认开）**：

| 状态 | 手机→PC | PC→手机 |
|---|---|---|
| 开 | 焦点切回自身时读取一次并推送 | PC 复制后直接推 `clip` 正文，手机纯被动写入 |
| 关 | 纯手动（「立即推送剪贴板」按钮） | 同上（接收始终纯被动写入；关掉的总开关只管本机要不要自动推） |

之所以后台也能收：Android 10+ 只限制**读**剪贴板（要求持有焦点），**写**没有限制。

**三处防回环**

| 机制 | 位置 | 作用 |
|---|---|---|
| `lastPushedSha1` | 手机 | 已推过的不再推 |
| `lastPulledSha1` | 手机 | 刚从 PC 拉来的不再回推 |
| `suppressSha1` | PC | 由协议写回的内容不再通知 |
| `lastClipEmitSha1` | 手机 | 同一份内容反复拉取时不重复处理 |
| `shouldSkipPeerClip(sha1)` | 手机 | 由 AppCore 比对**持久化**的 `lastPushedSha1` / `lastPulledSha1`：这条内容本机已经推出去过或已经拉回来过 → 不再重复写入剪贴板 |

前三者防的是"数据回环"，后两者防的是"重复写入"。
（2026-09-12 定版：剪贴板同步**不是发消息**，两端收到剪贴板帧都只写本机剪贴板 + 日志，**不生成聊天气泡、不进聊天记录**；冲突策略为简单后写覆盖。）

两个哈希（`lastPushedSha1` / `lastPulledSha1`）会**持久化到 SharedPreferences**，避免冷启动后把上一次已同步过的内容再回推一次。
